# PLAYBACK — demo and ghost playback

Status: **Phases A–E are built, tested and green** as of 2026-09-10. The
engine (A–D) was reconciled against `design/Overbounce Playback.dc.html`
(frames Pa, Pb, Pc, Pd, Pe, Pf) as it was written, so the easing model, the
in/out markers and the export config all come from that file rather than from
this plan's first guesses. Phase E built those frames and everything they
needed: `course-world.ts` (extracted from `main.ts`), `playback-session.ts`,
`ui/playback-chrome.ts`, `ui/screens/playback-library.ts`,
`render/video-export.ts`, plus the title screen's third entry and the app flow
that lets playback return to it. What Phase E did **not** build is listed at
the bottom under "Still not built".

Run the whole thing headlessly:

```bash
npm run demo-info -- <file.dm_68> [--entities]   # what a demo says about itself
npm run ghost-share-budget                        # how much run fits in a paste
npm run test:demo                                 # decoder
npx vitest run test/playback                      # the IR and the timeline
OB_DEMO=<file.dm_68> npm test                     # + the real-file checks
```

## What this is for

Two kinds of recording, one viewer:

- **Overbounce ghosts** — `GhostRun` (`src/game/ghost.ts`), a usercmd stream.
  Replayed by *re-simulating* it: same inputs, same integer-millisecond pmove,
  same positions. Already exists as an opponent to race; playback makes it a
  thing you can watch, scrub and film.
- **Quake III `.dm_68` demos** — a recorded *network stream*, not inputs.
  Nothing is simulated: the server already decided where everything was, 20
  times a second, and playback is decode + interpolate, exactly as
  `cg_predict.c`'s `CG_InterpolatePlayerState` does when `cg.demoPlayback` is
  set and prediction is off.

Those two are different enough that the temptation is to build two players. The
whole architecture here is the refusal to do that: both decode to **one
intermediate representation** (`PlaybackClip`), and the camera, timeline, export
and render layers only ever see that.

`src/demo/` and `src/playback/` join `src/physics/`, `src/collision/` and
`src/math/` in `eslint.config.js`'s `no-restricted-imports` boundary: no

that is where they get tested and where `tools/demo-info.ts` reads a demo
without a browser.

## Phase A — `.dm_68` decode (`src/demo/`)

### Reference sources

All fetched (`npm run download-assets -- --refs`). `cg_snapshot.c`,
`cg_predict.c`, `cg_playerstate.c` and `cg_servercmds.c` were **added to the
manifest by this work** — they were not there before, and they are exactly
where demo-side interpolation lives.

Read and transcribe, never recall (CLAUDE.md's rule, and the netfield tables are
the most recall-hostile thing in this project since the shader lump):

| What | Where |
| --- | --- |
| file framing | `cl_main.c :: CL_ReadDemoMessage` — `int seq`, `int len`, `len` bytes; `len == -1` ends the demo |
| message framing | `cl_parse.c :: CL_ParseServerMessage` — `MSG_Bitstream`, then one `MSG_ReadLong` (reliableAcknowledge) before the svc loop |
| gamestate | `cl_parse.c :: CL_ParseGamestate` — configstrings and baselines |
| snapshots | `cl_parse.c :: CL_ParseSnapshot`, `CL_ParsePacketEntities`, `CL_DeltaEntity` |
| bit IO | `msg.c :: MSG_ReadBits`, `MSG_ReadDelta*`, `msg_hData[256]`, `MSG_initHuffman` |
| Huffman | `huffman.c` in full |

### Files

- `src/demo/huffman.ts` — the adaptive Huffman tree. `Huff_Init`, `Huff_addRef`,
  `Huff_offsetReceive`, `Huff_getBit`. Decode only for now; the encode half
  (`Huff_offsetTransmit`) is needed by the **test writer**, so it is ported too
  and lives here rather than in test code — a writer built from a different
  understanding of the format proves nothing.
- `src/demo/msg.ts` — `MsgReader` (and `MsgWriter`, same reason). Faithful
  including the wart: `MSG_ReadBits` subtracts `nbits` from `bits` before the
  sign-extension check at the bottom, so a signed read of a non-multiple-of-8
  width sign-extends against the wrong width. Every signed read the protocol
  actually makes is 8/16/32, so it never fires — but the port keeps the shape
  and a comment, because "cleaner but different" is a regression here.
- `src/demo/netfields.ts` — `entityStateFields` (51 entries) and
  `playerStateFields` (48). **Order is the wire format.** Transcribed with
  their bit counts; the `0` bits mean "float", which is the
  `FLOAT_INT_BITS`/`FLOAT_INT_BIAS` integral-small-float encoding, not a raw
  32-bit float.
- `src/demo/state.ts` — `EntityState` and `DemoPlayerState`, plain objects
  shaped for the field tables (`pos`/`apos` as `Trajectory` from
  `src/game/trajectory.ts`, which is already the ported `BG_EvaluateTrajectory`).
- `src/demo/dm68.ts` — the container: iterate messages, decode gamestate and
  snapshots, expand every snapshot against its delta parent, return a
  `Dm68Demo`.

### The delta ring is not optional

`CL_ParseSnapshot` reads `deltaNum` as an offset back from the message sequence
and looks the parent up in a `PACKET_MASK` (32) ring. You cannot decode snapshot
N without having decoded its parent, and the parent is addressed by the *file's*
sequence numbers. So decoding is strictly sequential and one pass; random access
comes only afterwards, from the fully expanded snapshot array. That is why
`Dm68Demo` holds expanded snapshots in memory rather than an index into the file.

A 6-second DeFRaG demo is ~256KB on disk and expands to ~120 snapshots; a
10-minute demo is the size to worry about, and the answer if it ever bites is to
drop entity states for entities the viewer never draws, not to make decode lazy.

### What is decoded and what is skipped

Decoded: `svc_gamestate` (configstrings + baselines), `svc_snapshot`,
`svc_serverCommand` (needed for `cs` — configstrings change mid-demo, which is
how the map's own scores and `df_` fields update), `svc_EOF`. `svc_download` is
an error in a demo. `svc_nop` is skipped.

`svc_serverCommand` text is parsed only far enough to apply `cs <index> "<value>"`
and to keep the raw string for the (later) UI. Nothing here interprets `print`,
`chat` or `scores`.

### Metadata for the library list

- **map name** — `CS_SERVERINFO` (configstring 0), key `mapname`.
- **duration** — last snapshot `serverTime` minus first. NOT the run time in the
  filename: `coldrun[df.vq3.tr]00.06.536(q3a).dm_68` names a 6.5s *run* inside a
  demo that also holds the walk to the start and whatever happened after. The
  filename time is surfaced as a separate, clearly-labelled field when the
  DeFRaG pattern matches, never as the duration.
- **physics** — `CS_SERVERINFO`'s `df_promode` / `server_promode`. Absent means
  `unknown`, and `unknown` is what the UI shows. This project does not get to
  guess VQ3 for a demo recorded on a server it has never seen.
- **player name** — the POV client's `CS_PLAYERS + clientNum` configstring, key
  `n`; the model from key `model`.
- **protocol** — from the gamestate; anything but 68 is refused with a message
  naming the protocol found. 66/67 (Q3 1.27/1.29) and 71/73 (ioquake3, OSP,
  CPMA's own) have different netfield tables and are a different port, not a
  tweak.

### What the real demo settled

`npm run demo-info` against `demos/coldrun[df.vq3.tr]00.06.536(q3a).dm_68`
(a retail DeFRaG demo, local only — `demos/` is gitignored) decodes in ~290ms
and reports: map `coldrun`, 5739 snapshots **8ms apart** over 45.9s, physics
`vq3` from `df_promode 0`, POV `sarge`, 36–42 entities per snapshot, max
horizontal speed 3444ups, no origin step over 27.9 units.

Three things that fell out of reading the real file rather than the C:

- **`sv_fps` is routinely absent, and defaulting to 20 is wrong.** This demo
  ran at 125Hz (`defrag_svfps 125` in `CS_SYSTEMINFO`), and every one of its
  5738 gaps is exactly 8ms. `demoMeta` therefore MEASURES the rate from the
  modal gap (`measureSnapshotRate`) instead of reading a cvar that is not
  there. A 20 would have told a scrubber its finest step was six times
  coarser than the data.
- **`CS_SERVERINFO` carries a `protocol` key**, so a demo can be cross-checked
  against the protocol it is being read as. It is not how the protocol is
  decided — the file extension is — but a mismatch means the wrong netfield
  tables, which is otherwise a completely silent failure. `parseDm68` refuses
  it by name.
- **Unchanged entities are shared between snapshots, not cloned.** Nothing
  ever writes to a parsed `EntityState`, and a speedrun map's snapshot is
  mostly speakers and triggers that never move, repeated at 125Hz for the
  whole demo. Sharing them took the decode from 502ms to 290ms. Everything
  reachable from a `Dm68Demo` is therefore immutable by contract.

A mid-run snapshot is the clearest evidence the netfield tables are right, and
it is worth writing down because no synthetic test can produce it: at
serverTime 23832 the POV is holding `weapon 5` (WP_ROCKET_LAUNCHER), playing
`torsoAnim 135` (TORSO_ATTACK plus the toggle bit), pitched 86 degrees down,
climbing at +1364ups with `groundEntityNum 1023` and 7 rockets in
`ammo[5]` — a rocket jump, every field agreeing with every other.

### Verification

The repo pattern: a synthetic writer round-trip for traversal, plus an opt-in
real file for on-disk truth. Both are needed and neither substitutes for the
other — `test/collision`'s BSP writer has exactly this caveat written on it.

- `test/demo/huffman.test.ts` — compress/decompress round-trip over random
  bytes, and the tree state after `msg_hData` init (a wrong entry in that table
  corrupts everything after the first byte and nothing else would catch it).
- `test/demo/msg.test.ts` — bit reader/writer round-trip, delta entity and
  delta playerstate round-trip through the real field tables.
- `test/demo/dm68.test.ts` — write a synthetic demo (gamestate + a handful of
  snapshots with a moving player and one missile), read it back, assert every
  field survives.
- `test/demo/realdemo.test.ts` — **skips unless `OB_DEMO` points at a
  `.dm_68`**, the same shape `test/collision/realmap.test.ts` uses for `OA_MAP`.
  `demos/` is gitignored, so no demo is committed. Assertions chosen to be hard
  to pass by accident: first message is `svc_gamestate`; configstring 0 contains
  `mapname`; `serverTime` is monotonic and the gaps cluster at `1000/sv_fps`;
  the POV `ps.commandTime` is monotonic; consecutive POV origins never move
  further than a snapshot of movement can account for except across a
  teleport/respawn event.
- `tools/demo-info.ts` (`npm run demo-info -- <file>`) — map, protocol,
  duration, physics, snapshot count, entity-type histogram. Headless, and the
  fastest way to see a decode regression.

## Phase B — the playback IR (`src/playback/`)

### `PlaybackClip`

```ts
interface PlaybackClip {
  readonly meta: ClipMeta;           // kind, name, map, duration, physics, player
  readonly duration: number;         // ms
  seek(timeMs: number): void;        // may re-simulate; not required to be cheap
  sample(timeMs: number): PlaybackScene;
  dispose(): void;
}
```

`PlaybackScene` carries the POV player as a **`PlayerState`-shaped record**, not
a bespoke struct — `AnimatedPlayer` (`src/render/player-anim.ts`) already drives
MD3 frames from `legsAnim`/`torsoAnim` on a `PlayerState`, and a demo's
playerState netfields cover those plus `viewangles`, `weapon`, `pm_flags`,
`groundEntityNum`. One type means one renderer path for both sources.

Alongside it: `entities` (everything that is not the POV — other players,
missiles, items; empty for a ghost clip, which has its own missiles inside the
`Game`), and `events` (timestamped, so the render layer can decide what to
replay on a scrub).

### Sub-tick sampling

Export renders at 30/60fps; the physics tick is 8ms and a demo snapshot is 50ms.
Neither divides the other. `sample(t)` therefore returns the bracketing pair and
a fraction, and **the view layer interpolates** — nothing in `src/physics/` is
touched, and the integer tick stays integer. Angles lerp through `LerpAngle`
(shortest way round), origins and velocities lerp linearly, exactly as
`CG_InterpolatePlayerState` does.

### `GhostClip` — re-simulation, not baking

Baking a ghost to a position track was considered and rejected: the run's
missiles, decals, sounds and course events all come out of `Game`, and a baked
track would be a second, drifting definition of what the run looked like.

- Forward stepping is `Game.step` with the recorded cmd, the same loop
  `main.ts` already runs.
- Seeking backwards is reset + fast-forward with rendering off. 7500 ticks
  (a 60s run at 125Hz) is well inside a frame budget's worth of physics —
  `.agent/docs/perf-gate-findings.md` measures physics+collision+game at 4.1% of
  a real play trace — but it is not free with weapons in flight, so the clip
  keeps the **last** simulated tick index and only rewinds when the target is
  behind it.
- The `Game` is built by `src/game/ghost-sim.ts :: createGhostGame`, and
  `main.ts`'s `startGhost` is changed to call it too. **One definition.** A clip
  that built its `Game` with different `entities`/`axisLock`/`damage` would
  desync from the racing ghost in ways nobody would think to test for.

Golden test: re-simulating a stored `GhostRun` reaches `runState === 'finished'`
at exactly `run.time`. That is the determinism claim `ghost.ts`'s header makes,
asserted rather than assumed.

### `DemoClip` — decode + interpolate

Holds the expanded snapshots. `sample(t)` finds the bracketing pair by
`serverTime`, interpolates the POV playerState per `CG_InterpolatePlayerState`,
and evaluates each entity's `pos`/`apos` trajectory at `t` via the existing
`evaluateTrajectory` — Q3 entity motion is analytic, so a missile's path is
exact at any sub-snapshot time rather than lerped between two samples of it.

`nextFrameTeleport` matters: `CG_TransitionSnapshot` refuses to lerp across a
teleport, and so does this. Without it a teleporting player smears across the
map for one snapshot interval.

### Weapon numbering is a real trap

Overbounce's `Weapon` is `0..6` with `SHOTGUN = 6`. Q3's `weapon_t` has
`WP_SHOTGUN = 3`, `WP_ROCKET_LAUNCHER = 5`, `WP_PLASMAGUN = 8`. The IR uses
**Overbounce numbering**, and `src/demo/` maps `weapon_t -> Weapon` at decode
time with an explicit table. Neither numbering may leak into the other's type;
a demo weapon that Overbounce has no equivalent for (BFG, lightning, grapple)
maps to a `Weapon`-shaped `unknown` the renderer draws nothing for, rather than
to the wrong gun.

## Phase C — the timeline (`src/playback/timeline.ts`, `easing.ts`)

Headless and testable, which is the whole reason it is here rather than in
`src/ui/`. It is a pure function of time:

```ts
evaluateTimeline(timeline, timeMs) -> { camera: CameraDirective, look: LookOverrides }
```

- **Camera track** — segments, each naming a mode (`fpv` / `chase` / `side` /
  `free`) with mode-specific parameters. A `free` segment carries keyframed
  eye position, look-at (or yaw/pitch) and FOV.
- **Value tracks** — one per animatable scalar (fov, vignette, exposure,
  aberration, time scale). Photo mode's `PhotoLook` is the starting set, since
  those are the knobs that already exist as live post overrides.
- **Keyframes** — `{ time, value, ease }`. `ease` is per-*segment* (it describes
  the interpolation leaving this key), which is what an editor's per-handle
  easing means and what Instagram Edits does.
- **Easing** — `linear`, `ease-in`, `ease-out`, `ease-in-out` in `quad`,
  `cubic`, `quart`, `expo`, `sine`, `back`, plus `hold` (step). One table of
  pure functions on `0..1`, no library.
- **Cue points** — named marks with an optional action (`jump to`, `set speed`).
  They are data on the timeline; what a cue *does* is the UI's business.

Nothing in this file knows about `three`, a camera object, or a render pass. The
`CameraDirective` it returns is a description; the render layer applies it.

## Phase D — ghost sharing (`src/game/ghost-share.ts`)

The requirement is **paste into Discord**. That is a 2000-character message
(4000 with Nitro), and the current `GhostRun` JSON is roughly 60 bytes per tick
at 125 ticks a second — a 6-second run is already ~45KB. JSON is not the wire
format for sharing.

Encoding, in order:

1. **Binary ticks.** `forward`/`right`/`up` are already `int8` (`clampChar`).
   `yaw`/`pitch` become `uint16` **shorts** — and this is lossless, not a
   quantisation: `Simulation.step` puts both through `angle2short` before pmove
   ever sees them (`simulate.ts`), so the short IS what the physics ran on.
   `attack` and `weapon` pack into one byte.
2. **Delta-code** each field against the previous tick — a strafe-jumping run's
   yaw moves smoothly and its movement keys hold for hundreds of ticks.
3. **`deflate-raw`** via `CompressionStream`, which is available in every
   browser this game already requires for WebGPU, and in Node 18+ for the tests.
4. **base64url**, prefixed `OBG1.`. Decoding is whitespace-tolerant, because a
   paste through Discord and back will have line breaks in it.

### The measured budget

`npm run ghost-share-budget`, on a deliberately pessimistic synthetic run
(continuous mouse sweep, strafe key alternating every 20 ticks, periodic
weapon switches — a real run holds still more often, so this is a floor):

| run | ticks | JSON | shared | chars/s | fits Discord | fits Nitro |
| ---: | ---: | ---: | ---: | ---: | :---: | :---: |
| 1s | 125 | 14,176 | 601 | 601 | yes | yes |
| 6s | 750 | 84,157 | 1,111 | 185 | yes | yes |
| 15s | 1,875 | 210,208 | 1,811 | 121 | yes | yes |
| 20s | 2,500 | 280,194 | 2,149 | 107 | no | yes |
| 45s | 5,625 | 630,445 | 3,537 | 79 | no | yes |
| 60s | 7,500 | 840,515 | 4,275 | 71 | no | no |
| 120s | 15,000 | 1,680,906 | 6,852 | 57 | no | no |

**A run up to ~15s pastes into a Discord message; ~45s with Nitro.** Past that
it is a `.obghost` file drop, which the screen supports anyway. The cost per
second FALLS with length (601 chars/s at 1s down to 57 at 120s) because the
JSON header is a fixed ~500 characters that a longer run amortises — so short
runs are dominated by the header, not by their ticks.

That is better than the plan assumed and it does not change the conclusion:
paste is the primary path for a course-length run and the file drop is not
optional. Overclaiming here would be discovered by the first user with a
minute-long run.

The header (map, physics, camera, time, player, start snapshot) stays
human-readable-ish inside the compressed blob rather than being re-derived, so a
pasted ghost identifies its map before anything is simulated.

### The extraction, and how it was gated

`runCourse` 683–1576 was the only place a map got loaded and a scene got
built, and a playback session needs both. It moved to `course-world.ts`
mechanically — the same lines in the same order, wrapped in two functions —
which is the discipline `runCourse`'s own header records for the split that
produced it. Two functions rather than one because there is an ordering
dependency in the middle that cannot be flattened: `buildWorldSurfaces` needs
`movingSubmodels`, which comes off `Game.movers`, which needs the `entities`
that `loadCourseWorld` produces. The caller sits in that seam.

The gate is `npm run shot` on q3dm6 and de4th_run1, and it needs a caveat
learned the hard way: **the harness is not byte-deterministic.** Two shots of
identical code differ, sometimes a lot — one shot in five caught a different
frame of the map lights' flicker and came out ~9 mean-absolute levels from
every other shot *including its own siblings*. So a hash comparison proves
nothing, and a single before/after pair proves nothing either. What settles it
is a spread: five post-change shots plus the pre-change one, compared
pairwise. The pre-change shot sat inside the post-change cluster at the same
distance the post-change shots sat from each other (0.3–1.8 mean absolute,
against the outlier's ~9). That is the evidence the extraction moved nothing.

### `appFlow` is a graph now, not a funnel

It used to be "title once at boot, then course select forever", which was
accurate while course select was the only destination and nothing could go
back. Playback breaks both halves: it is a second destination reached from the
title, its rail offers Courses, and `Pd` offers "Back to title". One `place`
variable and one loop is what those edges actually are.

### Export: why not `MediaRecorder`

`MediaRecorder` over `canvas.captureStream()` timestamps frames from the WALL
CLOCK — it records what the machine managed to paint, drops frames when the
tab is busy, and produces a different file every run. `clip.ts`'s `frameTimes`
is written as the opposite promise. Honouring it needs `VideoEncoder`, which
emits raw chunks and no container, so `render/video-export.ts` carries ~200
lines of EBML to write a single-track WebM. There is no muxer dependency in
this repo and adding one for this was not worth it.

**Verified by round trip, not by eye.** Thirty encoded frames were pulled back
out of the muxed file, their SimpleBlock framing stripped, and fed to a
`VideoDecoder`: all thirty decoded, and the pixel at frame 10 matched the
colour that had been drawn into it. The keyframe's payload starts
`82 49 83 42` — the VP9 frame marker plus the VP9 sync code, at the right
offset.

A `<video>` element is NOT how to check this, and the attempt is worth
recording so it is not repeated: media playback is blocked in the automated
browser used here, and the control (a `MediaRecorder` file, known good)
stalled at `readyState 0` exactly as the hand-muxed one did. That control is
what proved the harness rather than the muxer was at fault.

## Still not built

Real gaps, listed rather than quietly accepted:

- **A demo's non-POV entities are decoded and not drawn.** `PlaybackScene.
  entities` is populated for a `.dm_68` — other players, missiles, items —
  and nothing renders them. A demo of a rocket jump shows the jump and not
  the rocket. This is the largest remaining gap, and it is render-side work.
- **A ghost clip's missiles are not DRAWN.** Its per-tick effects now reach
  playback (`PlaybackTickFx`, `GhostClip.takeFx`) and produce sound and
  decals, but nothing renders the missile in flight, the explosion sprite,
  the rail beam or the shotgun puff.
- **`CG_EntityEvent` is still not ported**, so entity events raise no sounds
  or effects.
- ~~No sound at all in playback.~~ Done in phase F -- `src/playback-fx.ts`.
- **A demo's movers do not move.** They arrive as entity states off the wire,
  and `buildCourseScene` is handed an empty `movingSubmodels` for a demo, so
  a door in a demo renders shut.
- **The side camera's cutaway is wired for the clip's OPENING camera only.**
  Switching to side later gets the camera without the cutaway; recompiling
  every world material on a camera change is not a trade worth making.
- **`bobCycle` is not interpolated** (`CG_InterpolatePlayerState` lerps it
  with a 256 wraparound; Overbounce's `PlayerState` has no such field).
- ~~Cue points have no UI.~~ Done in phase F.
- ~~Camera SEGMENTS have no UI either.~~ Done in phase N: `CAMERA MODE` is a

## Phase F: the feedback pass (2026-09-10)

Nine reported problems, and what each turned out to be. Written after the
fixes landed, because more than half of them had a cause that was not the one
the symptom suggested.

1. **In/out markers could not be moved.** TWO causes stacked, and fixing
   either alone leaves the bug. `draggable` measured its own event target,
   and `.ob-pb-marker` is `width: 0` (it IS a position; the grip is an
   absolutely-positioned child), so every drag resolved to time 0. And the
   ruler's `::after` hit-pad painted over the grips and swallowed the
   pointerdown. See `.agent/docs/playback-screens.md` §6.
2. **Cue points could not be removed.** There was no cue UI at all. Now:
   double-click the ruler to add, click a diamond to seek, double-click one
   to remove, plus a "+ Cue" button. The model side is `addCue`/`removeCue`/
   `findCue` and `CUE_EPSILON` in `playback/timeline.ts`, which is what makes
   "the cue I clicked" mean something on a ruler where one pixel is tens of
   milliseconds.
3. **No interpolation between cue points.** Cues are NAVIGATION marks and are
   deliberately not camera waypoints -- fusing them would mean a bookmark
   placed to find a moment also pinned the shot. What was missing was a way
   to key the camera AT THE PLAYHEAD: the only gesture before was a lane
   click on CAMERA POS, which keys position alone and only at wherever the
   lane was clicked. `K` / "+ Camera key" writes x/y/z/yaw/pitch/roll from
   the live free pose, and two of them interpolate on the picker's easing.
   Two bugs surfaced alongside: new keys inherited the PICKER's ease rather
   than `DEFAULT_EASE` (so one BOUNCE selection silently made everything
   after it bounce), and the camera track was applied AFTER `free.move` every
   frame, so a single key pinned the camera forever and the second key could
   never be placed. The rule now: the track owns the camera until you fly,
   and a seek or a play hands it back (`flying` in `playback-session.ts`).
   Authoring is therefore scrub, fly, key -- in that order, which the button
   tooltip says.
4. **Free camera would not move**, and 5. **LRNT was not supported.** One
   cause: the free camera read hardcoded `KeyW`/`KeyA`/`KeyS`/`KeyD` out of
   its own `held` set, where the game, photo mode and the pause menu all
   resolve through `KeyBindsStore`. `DEFAULT_BINDS` already ships
   `KeyL`/`KeyR`/`KeyN`/`KeyT` in the second slot of each movement action,
   so reading the store was the whole fix. Resolved locally rather than by
   constructing `createInput`, because that registers a canvas click handler
   that takes POINTER LOCK -- and playback must never lock the pointer, since
   every control on screen is a thing you click.
   One collision fell out of this and is worth knowing: `T` toggles the
   timeline AND is the default LRNT bind for "right". The movement bind
   wins while the free camera is active -- movement is the player's own
   configuration, and the timeline has an always-visible chip of its own.
6. **Clicking a cue should seek.** Part of 2. It listens on `pointerdown` and
   stops propagation, because the ruler underneath is a `draggable` that
   seeks on pointerdown -- without that, the press first seeks to the pixel
   under the diamond and only then to the cue.
7. **Sound and decals.** `src/playback-fx.ts`. A ghost hands over the whole
   `GameFrame` per tick (`PlaybackTickFx`), so it gets weapon fire,
   explosions, bounces, ricochets, pellet marks, pad and teleport sounds and
   mover sounds. A demo has only the POV's two-slot event ring, so it gets
   footsteps, landings, a jump and a fire -- `CG_EntityEvent` is still not
   ported and the alternative would be inventing sounds the demo never
   contained. Emission is gated on playing FORWARD, and a backward seek calls
   `Decals.clear()` (new): a rocket that goes off at 4s has no business
   scorching the wall at 2s.
   **Caveat worth knowing:** the bundled course paks carry no
   `gfx/damage/*_mrk` art, so decals are invisible on `ob_*` courses -- in
   the game too, not just here. Mount a pak that has them and they appear.
8. **ob_yard's skybox did not follow the player.** `renderAt` never called
   `sky.follow` or `shaderClock.set`. Both are now driven from CLIP time
   rather than a wall clock, so an export produces the same cloud position
   every run and a `timeScale` track slows the scrolling with everything
   else.
9. **Motion blur.** Three parts. The subject was never `markBlurExempt`ed, so
   the one thing the camera tracks was the one thing that smeared -- and that
   mark is now in `remarkPost()`, because a `PostChain` rebuild drops it the
   same way it drops the AO tags. A scrub teleports the camera and read as an
   enormous velocity, fixed by rendering one frame with `dtMs = 0` after a
   seek, which is already defined as "copy the position, zero the velocity."
   And `runCourse` passed `visualDt` (zero whenever frozen), which gave photo
   mode's flying camera no blur at all; `setMotionBlur` is entirely
   displacement-driven, so a parked camera gets zero blur whatever `dtMs`
   says, and passing the real delta is strictly more correct. Gated the way
   `.agent/docs/post-chain-drift.md` requires: `npm run photo-still` six
   times, 0/6 drift.

### Two clocks, and which one each thing runs on

Everything the picture is made of runs on CLIP time, and nothing runs on the
wall clock. `shaderClock`, the sky, and a decal's birth and fade all take
`t`. That is not tidiness: `runExport` renders frames as fast as the encoder
drains, so anything reading `performance.now()` would place its state
according to how long the frames BEFORE it took to encode -- and the README
promises "a slow machine produces the same video as a fast one." It is also
what makes a paused clip actually still, which is the rule
`npm run photo-still` gates for the game.

### Marks are state, sounds are events

The two are gated differently and it is deliberate. A decal is stamped
whenever the playhead moves FORWARD past the tick that made it, including on
a scrub-drag and inside an export -- a mark is world state and belongs on the
wall wherever the playhead is standing. A sound is only played while the clip
is actually running (`playing && !exporting`): dragging the scrubber across
four seconds is a forward move too, and firing every footstep in it at once
is a burst of noise rather than a scrub. Going BACKWARD is neither, and
clears the marks outright.

## Phase G: the second feedback pass (2026-09-10)

### One kind of mark, not two

The first pass shipped cue points (navigation marks on the ruler) alongside
camera keyframes (on the lanes), on the reasoning that a bookmark placed to
find a moment should not also pin the shot. The owner's answer was "why do
you have two buttons there?", and that settles it: from the outside there is
one thing, a marker on the timeline, and it is the keyframe.

So the cue button is gone and "+ Key" is the only one. The ruler's diamonds
are now `keyTimes(timeline)` -- every distinct time any track is keyed at --
so the marks at the top and the marks on the lanes are the same marks, drawn
once where the shape of the shot can be read and once where the detail is.
`addCue`/`removeCue`/`findCue` and `CUE_EPSILON` were removed with the
concept; `Timeline.cues` survives as an unused model field.

### Keys at 0:00.0, or interpolation has nowhere to come from

Opening the timeline now seeds every track with a keyframe at zero holding
its current value (`seedInitialKeys`). Without it, the first key a user
placed was a track's ONLY key -- and a single key holds its value across the
whole clip, so the camera did not travel, it sat at the keyed pose from the
first frame. "The interpolation does not really work" is the correct reading
of what that looks like. With a zero key, the first key you place is the
second of a pair and the shot moves from the opening frame.

Seeded once, and only for a track with no keys yet, so a zero key the user
has retimed is not overwritten on the next open.

### Two bugs behind "double-click does not remove a keyframe"

Both are about WHERE a gesture is recognised rather than about the gesture.

1. **The detector cannot live on the thing being removed.** The first click
   selects the key, selecting calls `renderTracks`, and that REPLACES every
   diamond in the lane -- so the second press arrived at a brand-new element
   whose detector had never seen a first press. No double could ever
   complete. The lane survives its own repaint (`innerHTML = ''` empties it),
   so the gesture is recognised there and the key is found by hit-testing.
2. **A 9px diamond rotated 45 degrees is about six pixels of real target.** A
   double-click that missed by two pixels fell through to the surface below
   and was read as "add one here". Both the ruler and the lanes now hit-test
   for a keyframe in PIXELS (`KEY_GRAB_PX`) over their full height, so a
   near-miss still means the keyframe. Pixels, not milliseconds: a
   time-based tolerance is most of the ruler on a four-second clip and a
   third of a pixel on a ten-minute one.

A third fell out while verifying: `keyCameraAt` writes six tracks but the
CAMERA POS row owns three, so removing "the row" left camYaw/camPitch/camRoll
keyed -- invisible, unreachable, and still bending the shot, with an
unaccounted diamond on the ruler. A camera keyframe is a POSE
(`CAMERA_POSE_IDS`) and is added and removed as one.

### A clip could play in total silence

`SoundSystem.play` returns early on a null `AudioContext`, and the context is
only created by `resume()`, which needs a user gesture. `runCourse` can hang
that on the click that takes pointer lock; playback never locks the pointer,
so a viewer who pressed nothing and just WATCHED never produced one. On top
of that, `play` drops any sound whose buffer has not decoded yet, so
preloading at the first click lost every event in the seconds that followed
-- which for a six-second defrag demo is the whole run.

Both now happen at session construction, where the decode overlaps the world
load. The listeners remain as a fallback and are deliberately not `once`: a
`resume()` that was refused has to be retried, not assumed.

### The decal art is in the bundled paks now

`gfx/damage/burn_med_mrk.tga`, `plasma_mrk.tga` and `bullet_mrk.jpg`, from
OpenArena's SVN and byte-identical to the copies in its own pak0 (verified by
sha256). They go in EVERY course kit via `DECAL_KIT`, because unlike a
texture set they are not a per-course choice. `decals.ts` builds no mark pool
for art it cannot load, so without them a bundled course showed no bullet
holes and no rocket scorches at all -- silently, in the game as much as in
playback.

### Still open

- **A demo's EXPLOSIONS are still missing.** The rocket now flies (see
  below); what remains is what happens when it stops, which arrives as
  `es.event` on entity states and needs `CG_EntityEvent` ported plus
  `PlaybackEntity` extended to carry `event`/`eventParm`. Also missing: the
  smoke trail and the rocket's dynamic light, both of which read
  `pos`/`trTime` trajectories the IR does not carry.
- **FPV motion blur is reported as much worse than the game's.** Not
  reproduced here: both call `setMotionBlur` with the real frame delta after
  the same `fpv.follow`, and both mark the same class of geometry exempt. The
  automated browser throttles `requestAnimationFrame` to ~100ms frames, which
  inflates measured camera speed far past what a real 60Hz frame produces, so
  the harness cannot judge severity. The one certain difference is that
  playback FPV draws no VIEWMODEL, so nothing in frame stays sharp the way
  the gun does in a run.

### Projectiles in flight (`render/missile-view.ts`)

A demo played a rocket's fire sound and its explosion sound with nothing
visible in between. The data was never missing -- `PlaybackScene.entities`
already carried the rocket (`eType` 3, `weapon` already mapped out of
`weapon_t`; the sample `coldrun` demo has 3476 such samples) -- and a ghost's
`collectMissiles` produced the same shape. Nothing drew them.

`runCourse` draws projectiles straight off `game.missiles`, which is right
*there*: it owns the simulation, so it has `pos.trDelta` and object identity
for free. Playback has neither, so the view takes the smallest thing both can
produce -- a stable number, an origin, and a kind -- and derives the rest.

Three things worth keeping:

- **Direction comes from the trail.** `CG_Missile` orients along
  `s.pos.trDelta`, the LAUNCH direction, which is why a Quake grenade points
  where it was thrown for its whole arc. A demo carries `angles` on the
  entity, but those are not what the cgame reads and are usually zero. The
  view aims the model along where the projectile has actually been
  travelling. For a rocket that IS `trDelta`; for a grenade it is the tangent,
  so an Overbounce grenade tips over where a Quake one would not. That is the
  price of the recording not carrying a trajectory.
- **A still frame must not stand the rocket on its tail.** Two consecutive
  frames at the same clip time -- a paused viewer, or an export rendering an
  exact timestamp -- give a delta of zero, and `orientAlong` answers a zero
  direction by pointing the model straight up (id's own `ent.axis[0][2] = 1`
  fallback). Seen and fixed: the last non-zero direction is remembered
  separately from the last position.
- **An index is not an identity.** `Game` keeps missiles in a plain array and
  splices dead ones out, so a rocket changes index the moment an older one
  explodes -- and anything remembering a projectile between frames then
  swings it to a different rocket's heading. `GhostClip` hands out numbers
  from a `WeakMap` keyed on the missile object, cleared on rewind.
  `test/playback/ghost-missiles.test.ts` pins this.

Still not drawn: the rocket's smoke trail and its dynamic light, both of
which read `pos`/`trTime` trajectories the IR does not carry, and a demo's
explosions, which are entity events (`CG_EntityEvent`, unported).

## Phase H: the timeline is direct manipulation now (2026-09-10)

Phase G replaced two kinds of mark with one, and left one kind of mark with
two ways to make it: a `+ Key` button and a click on a lane. That was the
remaining weirdness, and the owner named every part of it.

### There is no button

"Why does `+ Key` exist and why does it create two diamond shaped dots?" It
existed because keying used to need the camera pose, which the lane gesture
did not write. It made marks in two places at once -- one on the lane, one on
the ruler -- with no spatial relationship to where the pointer was, which is
what made it read as two separate things rather than one thing summarised.

Both go away by making the lane gesture complete. `K` remains as a shortcut
TO the lane gesture (`keyCameraAt` is now literally `addKey(cameraRow, time)`),
not as a second mechanism beside it, and nothing creates a mark anywhere the
pointer was not.

### Double-click was dead on arrival, and the cause is worth keeping

"Why can I not simply double click in the camera position and have my cue
point there?" Because a single click ADDED a key and a double press REMOVED
one -- and a double-click is two single clicks. So double-clicking bare lane
added a key, added it again over the top, then removed it, ending exactly
where it started with nothing on screen to explain why.

One gesture now owns both directions, on the lane as on the ruler: **on a
keyframe it removes, on bare lane it adds one there.** Single click no longer
creates anything; it only selects a key for the easing picker.

The general rule: never let a single click and a double click on the same
surface mean two different creative actions. The single click always fires
first, so the double click can only ever be "undo what the first click just
did", which is indistinguishable from nothing happening.

### CAMERA POS is the whole pose

"The interpolation only seems to work when `+ Key` was pressed." Exactly so,
and this was the reason: the button wrote six tracks (x/y/z AND
yaw/pitch/roll) while the CAMERA POS row owned three. Two gestures that drew
the same diamond, one of which made the camera travel and turn and one of
which only made it travel -- and removing "the row" left three angle tracks
keyed, invisible and unreachable, still bending the shot.

The row now owns all six. A cinematographer keyframes "the camera is HERE,
looking THERE"; that is one thing, so it is one row, one diamond, one gesture.

### The ruler summarises, and never creates

Its diamonds are the same keyframes the lanes carry, drawn once at the top so
"where does the shot change" reads without scanning five rows. Double-press
there removes a keyframe across every track at once; on bare ruler it does
nothing. Keys are made on the lane that owns them, which is the only place a
keyframe means something specific.

## Phase I: retiming, and the detonation nobody could see (2026-09-10)

### Diamonds drag

`moveKeyframe(timeline, id, from, to, duration)` retimes a key and reports
where it landed, carrying its value and its easing with it -- a drag is a
move, not a re-key, so dragging a BOUNCE key must not quietly relinearise it
or resample the camera pose.

It CLAMPS between the neighbouring keys rather than letting one pass another,
which is a real choice: a key that crosses its neighbour has to either swap
values with it or merge, and both are edits the user did not ask for while
dragging. Stopping at the neighbour is the one outcome that is always what it
looks like, and `KEY_MIN_GAP` keeps two keys off the same millisecond -- the
state everything downstream breaks on (two diamonds in one place, an
ambiguous click target, a zero-length span to interpolate across).

The gesture lives on the LANE, like the double-press and for the same reason:
each move re-renders the lane and replaces every diamond in it, so a listener
on a diamond would be thrown away mid-drag. The key is followed by TIME,
which survives those repaints in a way an element reference does not. A press
only becomes a drag after three pixels; below that it is a click, which
selects. And a press that became a drag calls `forget()` on the double-press
detector, or two quick nudges of the same key would delete it on the second.

**A bug worth keeping, because it is the third of its family.** The first
version moved the row's tracks in a loop that passed the *landed* time as the
next track's `from`. Only `camX` moved: the other five still had keys at the
old time, and asking them to move a key at a time they were not keyed at
found nothing. The lane looked right -- it draws `row.ids[0]` -- while the
ruler kept a diamond at the old place, because five tracks were still there.
Same shape as the CAMERA POS row that owned three ids while the button wrote
six. **Whenever one visible mark stands for several tracks, every operation
on it has to name all of them, from the same starting point.**

### Ghost playback drew no explosion at all

Reported as "no rockets, no explosions". The rockets were there -- but on a
rocket JUMP the missile lives two or three frames before it detonates at the
player's feet, so the model is effectively invisible and the burst is the
whole of what there is to see. And the burst was never drawn: playback played
the explosion sound and stamped the scorch with nothing in between, which
reads as the rocket having done nothing at all.

`ExplosionFx` (the real sprites) with `Effects` as the flat-colour fallback,
chosen the way `runCourse` chooses and honouring `?explosions=classic`. Fed
from the same `frame.explosions` that already drove the sound and the decal,
sized to the real splash radius -- 20 for plasma, 24 for a rail's ring, 120
for a rocket.

Aged on CLIP time with a CLIP-time delta, like the decals and the shader
clock: a `timeScale` track slows the fireball with everything else, a paused
clip holds it mid-expansion instead of running it out while the picture
stands still, and an export renders the same frame however long the encoder
took. A backward seek re-bases `lastFxTime`, or the next frame's delta is the
whole distance scrubbed, backwards.

Still not drawn: the rocket's smoke trail and its dynamic light, both of
which read `pos`/`trTime` trajectories the IR does not carry.

## Phase J: the gun in the hand, and the map's items (2026-09-10)

### The held weapon

`CG_AddPlayerWeapon` reads `cent->currentState.weapon` EVERY frame and hangs
that weapon's world model off `tag_weapon`, so what someone is seen holding
is a function of the weapon they currently have -- not something chosen once
when they spawn. The IR already carried exactly that: `PlaybackScene.weapon`,
mapped out of `weapon_t` on the demo side and off `Game.weapon` on the ghost
side. `AnimatedPlayer.setWeapon` already existed. Nothing connected them, so
every subject was empty-handed.

Ported from `runCourse` rather than shared with it, because the two differ in
where the weapon comes from (an IR sample against a live `Game`) and agree on
everything after that: the same `findWeaponItem(WEAPON_TAG[weapon])` lookup
that `CG_RegisterWeapon` does, the same per-weapon cache that
`weaponInfo->registered` is, the same stale-load guard, and the same
`markBlurExempt` -- the gun rides `tag_weapon` with the rest of the subject,
so it is exempt for the same reason the subject is.

### The map's items

`buildItemScene` was never called, so no armour, ammo, weapons or powerups
were drawn at all -- on a map like `ob_rockets` that is sixteen missing
objects.

Where the item list comes from depends on the source, and the difference is
real rather than cosmetic:

- A **ghost** hands over its own `ItemWorld` through the new optional
  `PlaybackClip.simulation`. A re-simulation knows which pickups this run
  took and when they respawn, so an item the runner collected disappears at
  the moment they collected it. `ItemScene.update` already hides what is not
  `present`; it only needed the right `ItemWorld`.
- A **demo** has no simulation, so its items are built from the map's own
  entities and stand where the map placed them. A `.dm_68` does carry pickups
  as `ET_ITEM` entity states and nothing reads those yet -- but a map drawn
  with all its items is much closer to right than a map drawn with none, and
  the alternative would be inventing a simulation a demo deliberately does
  not have.

Fog is computed once rather than per frame, as in `runCourse`: an item bobs 8
units, which cannot carry it out of a volume its resting position is well
inside. `update` runs on CLIP time, so a paused item holds its angle and an
export spins them identically run to run.

## Phase K: playback ignored every Display setting changed since page load

Reported as "I am in faithful mode, motion blur is set to 0, yet in fpv I
have motion blur". Both halves of that were true, and the second followed
from the first.

### The chain was built at boot and never told anything

`createRenderer` compiles the post chain when the page loads. `runCourse`
keeps it current with `applyLivePostOptions`. Playback did neither:

- It **never pushed** its own `basePost`, on a rule this plan previously
  wrote down as "never push the initial options -- the chain the renderer
  already has IS these values". That reasons from a premise which only holds
  if nothing has changed since boot. Pick Faithful 1999 on the title screen,
  then open a recording, and the chain still carries the blur stage from
  boot with `setMotionBlur` faithfully driving it.
- It opened Settings with **no context at all**
  (`showSettingsScreen(document.body, undefined, ...)`), so a change made
  from inside playback went to storage and nowhere else.

First person is where this shows worst, which is why the report named it: the
camera IS the eye, so every step is camera displacement and the blur is at
its strongest. Nothing about FPV was wrong -- it was just the loudest
speaker for a chain that had the wrong options in it.

The fix is one function, `pushPost`, that is the only thing which calls
`setPostOptions` and always follows with `remarkPost()`. It runs once at
startup, on every live Display change, and whenever a look track moves. The
old rule was solving the right problem the wrong way: what pushing cost was
the AO/lava/blur-exempt marks, and `remarkPost` is the answer to that, not
declining to push.

`RunPlaybackOptions.openSettings` now takes `PlaybackSettingsHooks`, so
Display, Audio and Controls changes all apply live -- the same R8 "no
reload" contract a running course has.

Verified by trace rather than by eye, which is the only way to be sure the
STAGE is gone rather than merely quiet:

```
11:31:50  post: tonemap agx, ... aberration 0.1, motionblur 0.2, ...   <- boot
11:32:06  post: tonemap agx, ... aberration 0.1, gamma 1, ...          <- playback
```

`motionblur` is absent from the third line, and `post.ts` documents
`setMotionBlur` as "a no-op when `?motionblur=0` took the stage out of the
chain entirely".

### A temporal dead zone that looked exactly like a dead button

Worth keeping because of how it presented. `pushPost` is a hoisted function
declaration, so calling it at startup type-checks and lints clean -- but it
assigns `lastLookKey`, which was a `let` declared two hundred lines further
down. Every session threw `Cannot access 'lastLookKey' before
initialization`, `runPlayback` rejected, and `main.ts` caught it and returned
to the library.

From the outside that is indistinguishable from "Start playback did not
register my click", and several minutes went into chasing the harness before
reading the console. **A screen that silently returns to where it came from
is a thrown error until the console says otherwise.** State that a hoisted
function touches belongs beside the state it is about, not beside the
function that uses it.

## Phase L: every handle drags, and a harness that can tell (2026-09-11)

Reported as "it is still not possible to drag the time start and end handles.
Clicking them should have priority over the time scrubber... The same should
be true for cue points."

### The markers lost the pointer to the ruler

Third report, and the first two fixes had both been real -- a `::after` hit
pad swallowing the grips, and a zero-width element being measured instead of
the ruler. This was a third cause underneath them, and the owner's own words
named it exactly: priority. The markers are children of the ruler, both are
`draggable`, and both handlers ran on one press. Each called
`setPointerCapture`; the last call of a dispatch wins, so capture went to the
RULER. The marker moved once, on the press, and then every move and the
release went to the scrubber instead.

An inner draggable now claims its press with `stopPropagation`. Capture
cannot be shared, so ownership has to be settled before the ancestor sees the
event. Two things fell out of that and are recorded as trap 16: a
bubble-phase `window` listener is starved by it (playback's audio wake, now
capture-phase), and without it the ruler's new retime armed on the keyframe
that sits under the in marker at 0:00 and dragged it away.

The grips also carry a grab offset now, so a handle moves WITH the pointer
instead of jumping under it on contact.

### Cue points drag, on one gesture that is decided at the press

A ruler press is a scrub on bare ruler and a RETIME on a diamond, chosen once
and held for the whole drag -- the pointer leaves the diamond immediately,
which is what dragging it means, so a per-move hit test would retime for one
frame and then scrub. Pressing a cue still seeks to it; below `DRAG_SLOP`
that is all it is.

The lane and the ruler now share `retimeKey`, which is where the "one mark,
several tracks, all from the same start" rule from trap 14 lives -- the fourth
place that rule would otherwise have had to be rediscovered.

### `npm run timeline-drag`

The reason this took three attempts is that no fix was ever verified with a
press, a move and a release. Two cheaper options are ruled out and both are
worth stating: `setPointerCapture` either throws or silently declines to
capture for a pointer that is not physically down, so a synthetic
`PointerEvent` cannot reach the line under test (and happy-dom has no capture
retargeting at all); and this
repo's usual automation emits move-then-press with no release, so it cannot
express a drag.

Puppeteer's mouse goes through CDP `Input.dispatchMouseEvent` -- trusted
input, a real pointer id, real capture. The tool mounts
`createPlaybackChrome` against a stub hooks object on a blank page
(`tools/browser/preview/timeline.html`), so it needs no clip, no pak, no BSP
and no adapter, and asserts thirteen things about four gestures.

It was checked BOTH ways: green on the fix, and six failures with one line
reverted. The discriminating assertion is not "the handle moved" -- a broken
build moves it too, on the press -- but **the handle moved and the scrubber
did not**.

### The crash found while verifying it

Working the timeline turned up a renderer crash with nothing in its stack
naming the file responsible:

```
Cannot read properties of undefined (reading 'matrix')
    at TextureNode.update  ...  at WebGPURenderer._renderTransparents
```

`ExplosionFx.update` derives a frame index from
`life = (now - born) / (until - born)` and clamps only the TOP. In a running
game `now` is level time and only rises; playback drives the same code on
CLIP time, and a backward scrub past a still-live burst makes `life`
negative. `frames[-1]` is `undefined`, `material.map` accepts it
(`noUncheckedIndexedAccess` is off), and three re-reads that property into
its texture node every frame -- so the next transparent draw dereferences
`undefined.matrix`.

Two fixes, because the clamp alone would have left the picture wrong: `life`
is clamped at both ends, and `ExplosionFx`/`Effects` grew `clear()` which
`PlaybackFx.reset()` now calls beside `decals.clear()`. A fireball whose
rocket has not been fired yet has no business still burning. Retired with
`Number.NEGATIVE_INFINITY` rather than `0`, because `until` is compared
against a clip time that is legitimately `0` at the head of a recording.

`test/render/explosion-scrub.test.ts` pins it, and was checked both ways.
Written up as trap 18 -- the general shape is that **any cgame pool with a
birth time is a clip-time hazard**, because the playback clock can run
backwards and can stand still, and no effect ported from cgame was written
for either.

## Phase M: the tracks show their value, and every edit can be taken back (2026-09-11)

`Pc`'s third column was structural -- 64px of placeholder per row. It is a
readout now, and the two gestures around it are built: drag the lane
vertically to set the value at the playhead, click the number to type one.
Undo and redo sit in the toolbar where the frame draws them, left of "Hide

### The units came out of the consumer, not out of the mockup

`Pc` prints `92°`, `35%`, `off` and `4px`. Three of those are real and the
fourth is not: `aberration` is a multiplier on 0.022 of the distance from the
centre of the frame, so its value in PIXELS depends on the frame's width --
`post.ts` measures the default 0.1 at 1.4px on a 1280-wide picture, which
makes `4px` a strength of 0.28 there and 0.14 at 2560. The raw strength is
printed. Written up as trap 19, whose general form is that a design frame is
a picture of the screen and not a specification of the model behind it.

Display ranges come from `src/ui/photo-mode.ts`, which already puts sliders on
exactly these four numbers, so the same value reads the same in both screens:
FOV 50..140 degrees, vignette and DOF 0..1 as a percent, aberration 0..1 raw.
`off` is a real state rather than a placeholder -- `createPostChain` does not
construct the vignette or aberration stage at 0 at all.

### Two gestures, one lane, decided at the press

A lane is a keyframe strip and a fader. The discriminator is what is UNDER the
pointer when it goes down -- a diamond means retime, bare lane means fader --
held for the whole gesture, which is the rule the ruler already uses for
scrub-versus-retime. Deciding on direction instead is unusable and deciding
per move flips the gesture one frame in; trap 20 has both.

CAMERA POS deliberately has no fader. The frame gives it `ns-resize` too, but
a camera pose is six tracks and is not a scalar; it keeps the word `drag` and
its double-press.

### `setValueAt`, because `setKeyframe` is the wrong tool for a playhead

Two failures it would have had, neither of them visible in a typecheck. It
matches a time EXACTLY, and the playhead is a float accumulated out of frame
deltas -- so a key at 4000 and a playhead at 4000.3 would become two keys
0.3ms apart, which is the state `KEY_MIN_GAP` exists to prevent. And it
assigns the ease, so every value edit would have flattened a key the user had
deliberately curved. `setValueAt` matches within `KEY_MIN_GAP` and leaves the
ease alone; pinned in `test/playback/timeline.test.ts`.

### Undo is a snapshot stack, capped at 50

`Timeline` is plain data, so `structuredClone` of the whole thing is the
complete state of every edit this screen can make. A command object per
operation would be six classes kept in step with the edits they mirror, for a
model that fits in a few kilobytes.

The restore is IN PLACE -- the session holds the same object by reference, and
assigning a fresh one undoes the edit in the lanes while leaving the picture
on the old timeline. A drag costs ONE entry: the press clones, the first move
past the slop pushes, a press that never travels drops it. Trap 21.

`playback-session.ts` gets `chrome.pushUndo()` for the one edit made outside
the chrome -- the camera cut `beginFlying` writes -- inside its guard, so a
held movement key does not push a snapshot per frame.

### `K` now refuses outside a FREE span

It was gated on the LIVE camera, which was the one place the CAMERA POS hatch
rule was not enforced: cut to chase at four seconds with the panel open and
the live camera is still free, so `K` at five seconds keyed a pose into a
hatched span where nothing will ever drive it.

Refuse rather than cut to free, for two reasons. `keyCameraAt`'s own comment
says there is one way to make a camera keyframe and `K` is a shortcut TO it --
and that one way, the lane's double-press, refuses. Making `K` cut would
re-create exactly the divergence that comment records. And the cut would not
be clean anyway: `freeStarted` means re-entering free cam does not re-seed the
flown pose, so `K` in chase would jump the shot to wherever free cam was last
parked and key THAT. The test lives in `chrome.keyCamera` so there is one rule
rather than two to keep in step.

> **Superseded by phase P.** The second argument is no longer true: the latch
> is gone and entering free cam re-seeds from the live view every time, so a
> cut would now be clean. The refusal stands on the first argument alone,
> which was always the stronger one -- one way to make a camera keyframe, and
> that way refuses outside a FREE span.

## Phase O: the gun in your own hands, and a chain that stops recompiling (2026-09-11)

### The view weapon

Ported from `cg_weapons.c` rather than recalled -- `CG_CalculateWeaponPosition`
(the bob roll/yaw/pitch, the landing dip, the idle drift) and
`CG_AddViewWeapon`'s `VectorMA` chain, with the `#if 0` stair-climb block kept
as a comment as CLAUDE.md asks.

Three things worth keeping:

- **`cg_fov` is a HORIZONTAL angle that in 1999 also pinned the vertical
  one.** three keeps `PerspectiveCamera.fov` vertical and widens
  horizontally, so feeding this camera's 16:9 horizontal fov (~122) into id's
  offset formula over-corrects and drops the gun almost out of frame.
  Measured all three ways; the 4:3-equivalent conversion is what reproduces
  Quake's placement, and it never reads the live aspect, so resizing the
  window does not slide the gun.
- **`bobCycle` was decoded and then dropped.** The demo path's
  `CG_InterpolatePlayerState` port names fields one at a time where id copies
  the whole struct, and a field nobody names is silently zero forever. The
  gun had no walk bob at all in playback until this was found; ghost clips
  did not carry the field either. NOT lerped -- it wraps at 256, and a blend
  across the wrap runs the phase backwards through the whole cycle.
- **Another clip-clock-runs-backwards bug, found independently.**
  `CG_CalculateWeaponPosition` tests `delta < LAND_DEFLECT_TIME` with no
  lower bound, because `cg.time` is monotonic in Quake. Scrub back past a
  landing and the dip evaluates against a negative delta and lifts the gun
  160 units out of frame, with no event left to correct it. Same shape as
  trap 18's explosion frame index. **Anything ported from cgame assumes a
  clock that only rises; playback's does not.**

The landing dip is NOT gated on `audible` the way the sounds are. A dip is
picture, so gating it would put a different frame in the export than on
screen, which is exactly what `frameTimes` promises does not happen.

### The look values are uniforms now

`setPostOptions` recompiles the chain, and a timeline that keyframes vignette,
aberration or exposure changes one every frame -- so scrubbing such a clip was
a shader rebuild per frame, and so was every frame of a photo-mode slider
drag. `Renderer.setPostLook` writes three uniforms instead.

What did NOT change is whether a stage EXISTS: `.agent/docs/post-chain-drift.md`
measured that an always-present stage sitting at an exact identity still moves
the paused still frame off byte-identity in one run of six. So a value moving
inside a live range is free and a value crossing its boundary still rebuilds,
once. `lookNeedsRebuild` is that boundary test, exported for its own test
because it is the one piece that can be wrong invisibly -- backwards one way
and every frame rebuilds anyway, backwards the other and the value goes into a
uniform no compiled shader reads.

That change also closed a confound the drift investigation had left open: its
table never separated literal from uniform. Twelve clean runs on q3dm6 say a
uniform in the final pass is not what drifts.

## Phase P: "the free camera resets to spawn", and one row easing a sixth of the shot (2026-09-14)

Two reports, and neither one was where it looked.

### The free camera: three seeds, none of which was the one the shot used

"When switching to free cam, the current camera position should be used as a
reference point; it looks as if it's currently reset to spawn." True, and
there were **three** separate reasons for it stacked on top of each other. The
third is the one that actually produced the picture, and it is the one no
amount of staring at `playback-session.ts` would have found.

**1. `freeStarted` was a latch.** `seedFreeFromView` returned early once it had
run, so the seed was a one-shot per session: enter free cam, fly somewhere,
cut to FPV, cut back to free, and the shot jumped to the pose free cam had
been left at rather than the one on screen. Park it near the spawn once --
which is where anyone parks it, because that is where a clip opens -- and
every later entry sent the camera back to the spawn.

**2. A free SEGMENT never seeded at all.** `setCamera` was the only caller, and
`activeCameraAt` reads `timeline.cameras` directly without going through it. So
a playhead crossing into an unkeyed free span found the free camera still at
its constructed `[0, 0, 0]`, the world origin, usually inside the floor.

Both are gone because the seed is **edge-triggered in the frame** now: any
frame where the active camera becomes free, from any of the three paths (a
CAMERA pill, a held movement key through `beginFlying`, or the playhead
entering a segment), starts the free camera from the eye the previous frame
was rendered through. `prevActive` is the edge, written after the camera
switch; `freePlaced` is what is left of the latch and serves exactly one
caller, `cameraPose`, which may be asked where the free camera is before any
edge has fired.

The angles come from the render camera's own facing now rather than from the
subject's `viewangles`. In FPV those are the same thing; in SIDE and CHASE they
are not, and seeding from the subject whipped the view round to whatever the
runner happened to be facing. Both conversions moved into `poseFromCamera` in
`render/photo-camera.ts`, beside the `apply` they invert, because that pair is
only checkable side by side -- and getting it backwards is a failure this repo
knows by sight: the camera lands in a wall, the jump is enormous, and the
motion blur smears the frame, which reads as a renderer bug. `test/render/
photo-camera.test.ts` is the round trip; flipping one sign fails it.

**3. And the shot still went to the spawn, because `seedInitialKeys` was
overwriting the seed every frame.** This is the real one. Opening the timeline
panel seeds every track with a key at 0:00 holding its current value, CAMERA
POS included -- and that key is written from `cameraPose()`, the LIVE pose, at
whatever moment the panel happened to be opened. A single key holds its value
across the whole clip. So on a side-locked map: open the panel at the start,
get a camera key holding the side camera's eye near the spawn, and from then
on every cut to FREE put the shot back there, no matter where the playhead was
or what was on screen. The session's own seed ran correctly and the track
replaced it one frame later, forever.

The fix is one line and it is not a special case: **`seedInitialKeys` seeds
CAMERA POS only when the camera at 0:00 is already FREE**, which is the rule
the lane's own double-press already enforces -- a key in a hatched span has
nothing to drive it. `seedInitialKeys` was the one writer that broke it, and
its own doc comment had gone stale saying otherwise ("the chrome runs this
AFTER `hooks.setCamera('free')`", which stopped being true when opening the
panel stopped forcing free cam).

The camera does not need the zero key the scalars need, and the asymmetry is
real rather than a concession. A scalar is keyed to RAMP, so one key with
nothing before it is a ramp with no start -- that is what phase G's "keys at
0:00.0" was about. A camera pose is keyed to BE somewhere, and a free span
with no keys now starts from the eye the shot was already on, so the pair a
move needs is the two keys the user places and neither of them is a pose
nobody chose.

**The trade, stated so it is not "fixed" back:** parking the free camera,
looking at FPV and returning no longer comes back to the parked pose. The pose
is a keyframe's job, which is what CAMERA POS is for. "The camera you are
looking at is where free cam starts" is the rule now, on every path.

`PLAYBACK.md`'s phase M paragraph on `K` cited the latch as a reason -- "`freeStarted`
means re-entering free cam does not re-seed the flown pose, so `K` in chase
would jump the shot to wherever free cam was last parked". That sentence is no
longer true. The refusal it argued for is still right, and now for the simpler
reason: `keyCameraAt` is one way to make a camera keyframe and the lane's
double-press refuses outside a FREE span, so the shortcut TO it refuses too.

### Easing wrote a sixth of the camera

"Easing functions are not properly implemented." The curves in `easing.ts` are
complete and correct; the picker was writing them to one track out of six.

A selection carries one `TrackId` because that is what a diamond is drawn from
(`row.ids[0]`), and for FOV, VIGNETTE, DOF and CHROMATIC AB. that is the whole
row. CAMERA POS is one mark over six tracks, so EASE OUT CUBIC on a camera key
eased `camX` and left `camY`, `camZ`, `camYaw`, `camPitch` and `camRoll`
linear: the move arrives, along a path nobody authored. Invisible on four rows
out of five and total on the fifth -- the one a camera move is actually
composed on.

`track-list.ts`'s `retimeKey` already states the rule and lists the three times
it has been broken: **whenever one mark stands for several tracks, every
operation on it has to name all of them.** That is now four; the picker was the
last writer that did not. It resolves the row through `TRACK_ROWS` and writes a
COPY of the `Ease` to each key -- a copy because `Ease` is mutable and one
object shared by six keyframes would make a later edit to any of them silently
rewrite the other five, which is the same class of bug wearing the opposite
sign.

`test/ui/ease-picker.test.ts` pins it, on the MODEL rather than on the button
classes: the defect was never visible in the picker, which lit up EASE OUT
CUBIC correctly while writing it to a sixth of the shot.

### Two consequences of moving the seed into the frame, both deliberate

Neither is a bug, and both look like one if you meet them without this.

- **The first mouse delta of a look-drag entry is dropped.** The pointermove
  handler calls `beginFlying()` and then `free.look(dx, dy)` synchronously;
  the edge seed fires on the next frame and overwrites those angles. It is one
  frame of one drag -- about a degree -- and the alternative is a second seed
  path in `setCamera` that has to set `prevActive` too, to avoid seeding
  twice. Not worth two paths for a degree.
- **A seek across a mode boundary seeds from the PRE-seek eye.** Scrub from
  1s in SIDE to 5s in an unkeyed FREE span and the free camera starts at the
  side camera's 1s position, because `renderAt(time, 0)` runs the edge with
  `r.camera` still where the last frame left it. That is "the shot does not
  jump" applied literally, and it is the rule: free cam starts from the
  picture you were looking at, including when the picture you were looking at
  was four seconds ago. A viewer scrubbing a long way forward will see the
  runner leave frame, which is what a free camera does.

### The one gap this made WORSE, not just visible

> **Closed in phase Q**, below. Kept because the reasoning is the reason
> `ANGLE_TRACKS` is an explicit set rather than a name test.


`evaluateTrack` lerps `camYaw` as a plain scalar, so two keys at 350 and 10
sweep 340 degrees the wrong way. That was always true and was always hard to
reach, because `PhotoCamera.look` accumulates yaw unbounded -- fly past 360
and the numbers keep climbing, so successive keys stayed continuous.
`poseFromCamera` returns `atan2`, which is `(-180, 180]`. So: fly to yaw 370,
key it, cut away, cut back (the seed now gives ~10), fly a little, key again
-- and the two keys are 360 apart in the model with nothing on screen to say
so. The camera spins through a full turn between them.

The latch used to prevent this by accident, by never re-seeding. The fix is
shortest-arc interpolation for the three angle tracks, which is a real change
to `evaluateTrack` (it would need to know which ids are angles) and is not in
this phase. Listed with the rest of the absences rather than done quietly.

### Verified in a browser, on a real clip

Not on the fixture -- `timeline-drag.ts` drives the chrome with no session
behind it, so it can see a keyframe move and can never see where a camera
went. A synthetic `ob_basics` ghost injected into `localStorage` (plus a
matching `overbounce.records.v1` entry, since the library lists ghosts by
walking the record book) is enough to reach the real playback screen, and all
three of the above show up immediately there and nowhere else.

Both halves confirmed: cutting to FREE at 0:04.1 holds the shot instead of
returning to the spawn, and a SECOND entry at 0:01.0 after having been in free
cam at 0:04.1 takes the side camera's current eye rather than the parked pose.

## Phase Q: the time scale has a lane, and angles take the short way (2026-09-14)

Two of the absences enumerated at the end of phase P, taken in order.

### TIME SCALE was wired end to end and had no control

`timeScale` was read by the playback loop (`time += dt * timeScaleAt`) and had
no row in `TRACK_ROWS`, so slow motion existed in the engine and could not be
reached from anywhere. That is worse than an unbuilt feature: an unbuilt
feature is honest about itself.

It is a SIXTH row and `Pc` draws five, which is recorded in the row's own
comment the way `easing.ts` records the three families it implements and does
not offer. It goes **last**, and that is load-bearing rather than tidy:
`tools/browser/timeline-drag.ts` addresses FOV as `:nth-child(3)` of the track
list, so a row inserted above it moves every assertion in that harness onto a
different lane -- and the harness would still pass, because the rows it would
then be dragging are also faders.

The range is 0.1 to 4, and the floor is the interesting end. `timeScaleAt`
clamps positive at 0.01 because a zero or negative scale is a paused or
reversed clip and the transport owns both, so a fader that could reach 0 would
offer a freeze the model refuses to give -- the readout and the picture would
disagree about what the user had just done. Every write goes through
`setRowValue`, which clamps to the row's own range, so neither the drag nor
the typed field can get there.

A new `multiplier` unit prints `0.50x`, because a bare `0.50` in a column of
`100°`, `35%` and `0.10` is the one reading that could be anything. `parseValue`
strips `x` as well as the multiplication sign the cell prints: that character
has no key on a keyboard, and rejecting the letter would make TIME SCALE the
one row whose own printed value could not be typed back into it.

**The export had to change too, and this is the half that mattered.**
`frameTimes` stepped uniformly through clip time, so a span marked 0.5x played
slow on screen and exported at full speed -- the shot on screen and the shot
in the file would have been different shots, which is the one thing that
function exists to prevent. With a `timeScale` track the walk is now
incremental, advancing each output frame by `interval * timeScaleAt`, exactly
mirroring the loop. That gives up the "no accumulated error" property the
uniform form had, and it has to: the step depends on where the walk is, so
there is no closed form for the Nth timestamp. It gives up nothing else -- the
walk is still a pure function of the timeline and `fps` with no wall clock in
it, so two exports of one timeline are still identical. **Without such a track
the exact uniform form still runs, unchanged**, which is every clip nobody has
keyframed; a test pins that equivalence.

The loop is capped at a hundred output frames per source frame. `timeScaleAt`'s
clamp already guarantees progress, so the cap is a guard against a future
change to that clamp rather than against anything a user can set.

**The audio does not follow.** Export sound is captured off the same frame
loop, so a slowed span gives slowed picture against sound at its own rate.
Pitching audio is a resampling problem, not a timeline one, and it is not
solved here.

### Angles take the short way round

`evaluateTrack` lerped `camYaw` as a plain scalar, so two keys at 350 and 10
swept 340 degrees the wrong way. Phase P made that reachable where it had been
theoretical -- see its own note -- so it is closed here with `lerpAngle`,
which is `q_math.c`'s `LerpAngle` and already what `demo-clip.ts` and
`ghost-clip.ts` interpolate every other angle in this project with. This was
the one place doing it by hand.

`ANGLE_TRACKS` is an EXPLICIT set (`camYaw`, `camPitch`, `camRoll`) and not a
name test, because "looks angular" is not a property a track has: `fov` is
degrees too, and 350 to 10 degrees of field of view is not a short path, it is
a different lens. A test asserts the set by value for exactly that reason.

Two orderings are worth stating because both are wrong the other way round.
**The ease shapes the fraction and the wrap decides the path**, in that order
-- easing the wrapped result would ease a number that had already taken the
long way, giving a smooth curve along the wrong arc, which reads as deliberate
and is therefore worse than the linear failure. And the result is **not
normalized**: 350 to 10 passes through 360, `angleVectors` neither knows nor
cares, and folding it to 0 would cost the one thing that makes the arithmetic
readable in a debugger.
