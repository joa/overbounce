# PERFORMANCE — steady 60fps, no functional change

Status: **phase 0 complete. Phase 3 (the HUD) complete. Phase 2A's matrix half
complete.** Phases 1 and 2 are not started.

Phase 3 result, measured: `hud.update()` went from **967µs to 198µs** per frame
on a realistic in-game frame (clock, splits and strafe gauge all live) — a 4.9x
reduction. The rendered DOM is byte-identical before and after, verified two
ways: `test/render/hud-dom.test.ts` compares whole-subtree markup across 13
cases in happy-dom, and the live HUD's `outerHTML` was diffed out of real Chrome
against the unmodified build. See 3.0 and 3.1.

Phase 0 changed several things this plan had assumed. All of it is measured, all
of it is in `.agent/docs/perf-gate-findings.md`, and the three that matter most
are folded into the text below:

- **The frame is CPU-bound, and the spikes are gameplay's.** Measured on q3dm6:
  `cpu 8.3ms / gpu 1.6ms`, p50 9.1ms, p99 15.3ms, worst frames 62-75ms. Idle sits
  at p50 7.0 / p99 9.7 / max 33.6, so both the median cost and the spikes grow
  when the player actually moves and shoots. That is the case this plan was
  written for, and it survives contact with a profiler.
  (An earlier draft of this note said the opposite. The first four profile runs
  reported `gpu 11.9ms` and "GPU-bound" — that was Chrome throttling the page to
  10fps and a `gpu` timestamp that included the vsync wait. Same scene, same GPU,
  1.6ms once the throttle is off. See finding 7.)
- **GC is ~1% of the frame, so "reduce GC pressure" is not by itself the route
  to 60fps.** A 63s DevTools trace of real play puts main-thread blocking GC at
  0.68% of wall time and 2.26% of time inside the frame callback. It still
  matters for the *tail* — incremental-marking bursts of 10-22ms land inside
  individual long frames, and those are allocation-driven — but four of the
  twelve worst frames contain no GC at all. Phase 1 trims the tail; it does not
  move the mean. Say which is being claimed.
- **The CPU ranking is now measured, and it is not what this plan assumed.** All
  of phase 1's territory (physics + collision + math + game) is **4.1%** of busy
  CPU. `hud.ts` alone is **8.6%**, and three.js is **53%**. See 0.6.
- **A flat brush list never enters the BSP walk**, so the first draft of this
  gate had zero coverage of the hottest allocation site in the project. Fixed;
  see 0.5.

The goal is a frame time that is *flat*, not merely low. A 60fps average with a
7ms GC spike every two seconds reads as stutter, and stutter is worse in this
game than in most: a speedrunner is reading a strafe gauge and an overbounce
letter frame by frame.

## The one rule that governs every change below

**No observable output may change.** Not physics, not render, not HUD text.
Every item here is one of exactly three transformations:

1. **Pool** — move an allocation out of a hot path to module/closure scratch.
2. **Precompute** — move work that cannot change out of the per-frame path.
3. **Skip** — do not do work whose result is thrown away or is unchanged.

Explicitly **not** on the table: rewriting arithmetic. No `Math.hypot` ↔
`sqrt` swaps, no reassociation, no dropping a `fround`, no reordering of
operations inside `src/physics/` or `src/collision/`. Per CLAUDE.md the fround
chains and the `#if 1` branches are the product. A change that is 3% faster and
moves an overbounce spot by a quarter unit is a regression.

## Phase 0 — measure and gate, before touching anything

This phase is what makes "no functional change" enforceable rather than hoped
for. Do not start Phase 1 until it is in place.

### 0.1 Golden replay baseline — DONE

15 scenarios in `test/golden/scenarios.ts`, snapshots in
`test/golden/snapshots/*.tsv`, checked by `test/physics/golden.test.ts`,
regenerated by `npm run golden`. Full precision, never rounded: `tools/replay.ts`
prints `toFixed(3)` for humans, and a gate that rounds misses exactly the
sub-unit drift a missed `fround` causes.

Coverage: strafejump (800 ticks, 1129ups peak), overbounce, walk-flat, slick,
ramp, stairs, ledge-drop, wall-slide, obstacles, cpm-air, cpm-ramp, rocketjump,
jumppad, teleporter, door-ride.

**Nine of them also run against a compiled BSP and must produce the same file.**
That is not redundancy — see 0.5. It is the only tree-walk coverage there is.

Sensitivity, measured: perturbing `OVERCLIP` from 1.001 to 1.0010001 fails
`ledge-drop` at tick 210, on the seventh significant digit of `oz`. Only one of
fifteen caught it, because `SnapVector` rounds velocity to integers each tick and
absorbs perturbations until one crosses a rounding boundary. A realistic
regression is orders of magnitude larger and lands in many scenarios at once, so
the set passing is the signal, not any one of them.

### 0.2 Standing test gates

Every phase re-runs, in this order:

    npm run test:physics     # golden snapshots + allocation gate + the rest
    npm run test:collision   # trace isolation + the tree-vs-flat-list differential
    OA_MAP=/path/to/map.bsp npm test   # after anything touching src/collision/
    npm run typecheck && npm run lint  # no-any + the import boundaries

The `OA_MAP` run matters more than it looks, after finding 3 in 0.5: a real
`.bsp` has a deeper, less regular tree than `writeBsp` produces, and it is the
only thing within reach that might exercise a mid-point aliasing bug the
synthetic trees cannot.

`test:collision` asserts that a tree walk and a flat list produce *the same*
trace, which is the right shape of gate for 1.1 and 1.2 — but see 0.5 for how far
it actually reaches. It catches a pooled `TraceWork` that corrupts the sweep; it
demonstrably does **not** catch a mid-point buffer aliased across recursion
depth.

### 0.3 A zero-allocation regression test — DONE

`test/physics/allocation.test.ts`, with `--expose-gc` plumbed to the vitest
workers through `vite.config.ts`'s `poolOptions`. Measures retained bytes **per
tick** — not a total, which would make the test's strictness an accident of how
long it happens to run — over 20 000 ticks, after 4 000 of warmup, with a forced
collection at each end.

Calibrated on this tree: steady state is 0.6-3.0 bytes/tick against a threshold
of 24; one deliberately leaked `vec3()` per tick reads 243 and fails all three
cases. The suite skips itself if `global.gc` is missing, and a separate
always-on test fails in that case, so a lost flag cannot pass as a green run.

**Know what it does not measure.** A short-lived scratch `vec3()` is reclaimed by
the forced collection and never appears at all. This catches *leaks and
accumulation*, not *churn* — and churn is what costs frame time. Phase 1's
success is therefore not measurable here; that is 0.4's job. What this buys is a
hard stop on the likeliest way to get 1.5 wrong: a pooled object that
accidentally retains the previous frame.

### 0.4 One real profile before optimizing the wrong thing — DONE

`src/render/stats.ts` already separates `cpu` / `gpu` / `draws`, and its own
header comment warns that fps is vsync-clamped and therefore blind. Take one
Chrome DevTools performance recording of a live run (with the allocation
sampler on) and record in `.agent/docs/`:

- minor-GC cadence and cost — is GC actually a spike source here, or is the
  frame budget going to `gpu`?
- the `cpu` split between the physics ticks and the render-side per-frame block.

If `gpu` turns out to be the limiter, that is a finding worth writing down and
a separate plan — but the GC work below was asked for regardless, and it is
where the *spikes* live even when the *average* is GPU-bound.

Built as `npm run profile` (`tools/browser/profile.ts`), on top of the existing
isolated-browser harness. It drives a real map with real input — forward,
strafing, jumping, firing — verifies the player actually moved, and reports the
game's own `cpu`/`gpu` alongside a sampled allocation ranking.

**Result: the frame is CPU-bound, and gameplay both costs more and spikes more.**
q3dm6, 1280x720, median of three 12s runs:

| | fps | cpu | gpu | p50 | p90 | p95 | p99 | max |
|---|---|---|---|---|---|---|---|---|
| playing | ~112 | 8.3 ms | 1.6 ms | 9.1 | 10.6 | 11.3 | 15.3 | 62-75 ms |
| idle | ~142 | — | — | 7.0 | 8.3 | 8.7 | 9.7 | 33.6 ms |

Three things follow, and the plan below depends on all of them:

- **CPU is the budget**, at roughly 5× the GPU. Work removed from the frame
  callback is work removed from the critical path.
- **Playing costs about 2ms/frame more than an idle camera** — the physics ticks,
  missiles, dynamic lights, effects and the shadow trace. The other 7ms is there
  whether or not anyone is playing, which is what makes phases 2 and 3 worth as
  much as phase 1.
- **The spikes are real**: p99 goes 9.7 → 15.3 and the worst frames 33 → 75ms the
  moment gameplay starts. A 70ms frame is four dropped in a row. Whatever causes
  them appears exactly when allocation does, so GC is a plausible cause — but
  **not a proven one**, because the profiler cannot see `Float32Array`. Do not
  write it up as established.

**The measurement trap that gave the opposite answer first**, recorded because it
is easy to repeat: Chrome throttles a page it thinks nobody is watching (headless
*and* headful) to about 10fps, and under vsync the `gpu` timestamp measures the
wait rather than the work. That combination read `gpu 11.9ms` and said
"GPU-bound". The flags now in `profile.ts` — `--disable-background-timer-throttling`,
`--disable-backgrounding-occluded-windows`, `--disable-renderer-backgrounding`,
`--disable-gpu-vsync`, `--disable-frame-rate-limit` — take it to ~115fps and
`gpu 1.6ms`. It also inflated `cpu`: at 100ms per callback the accumulator runs
~12 physics ticks instead of 2 (`MAX_CATCHUP_MS` is 200, nothing clamps it) and
charges all twelve to one frame.

**Three things this profile cannot tell you**, each measured rather than assumed
and each capable of producing a confidently wrong conclusion:

1. **The allocation ranking is blind to `Float32Array`** — 300 000 escaping
   `Float32Array(3)`s attribute 0.00 MB where the same count of plain `{x,y,z}`
   attribute 0.19 MB (`tools/browser/sampler-blindspot.ts`). `vec3()` is a
   `Float32Array`, so all of `src/physics/`, `src/collision/` and `src/math/` is
   invisible. The first run duly ranked physics at ~0% with the player moving at
   381ups. **Use the profile to rank phases 2 and 3. Never phase 1.**
2. **`onMouseMove`/`onKeyDown` near the top are not our garbage** — those
   handlers allocate nothing; the bytes are the browser's own event objects.
3. **Neither `gpu` nor any percentile means anything without the anti-throttle
   flags.** They are in the tool now; if they are ever removed, every number it
   prints reverts to measuring Chrome's power management. `--headful` is *not*
   the fix — the throttle applies there too.

Still outstanding, and the only route left to attributing the spikes: a DevTools
timeline recording with the GC track. That would turn "the spikes appear when
allocation does" into "the spikes are GC", which is currently an inference.

### 0.5 What the gate structurally cannot catch — READ BEFORE PHASE 1

Three limits, every one measured rather than assumed.
`.agent/docs/perf-gate-findings.md` carries the numbers.

1. **A flat brush list never enters `traceThroughTree`.** `brushListModel` sets
   `nodes: []`, so `traceInternal` jumps straight to `traceThroughLeaf`.
   Counted: `flatlist_nodes=0` for every scenario, against `bsp_nodes=31118` for
   strafejump alone. The `runBsp` variants exist for exactly this and are the
   only tree coverage in the suite. **Any new synthetic-world test inherits this
   blind spot** — check which path your world reaches before trusting it.
2. **Point traces do not occur in physics.** One in the entire scenario set (a
   missile), against roughly 14 000 box traces. The real point traces are the aim
   laser (`aim.ts:168`) and missile tracing, both render/game side and both out
   of a headless gate's reach. `test/collision/trace-isolation.test.ts` covers
   the branch by construction instead.
3. **The mid-point aliasing hazard has no failing test.** Replacing
   `traceThroughTree`'s `mid`/`mid2` with two shared module buffers — the exact
   bug 1.2's depth-indexed stack is meant to avoid — passed all 1151 tests,
   including a scenario built specifically to be sensitive to leaf selection, and
   produced a byte-identical leaf-visit sequence (2691 visits, same order). Do
   the depth-indexed stack anyway; just do not expect red if you get it wrong.
   **Review that one.**

## Phase 1 — physics and collision (highest frequency, smallest share)

At 125Hz the physics tick runs roughly twice per 60fps frame, and each tick
issues many traces (slidemove bumps, ground trace, step up/down,
correct-all-solid). This is the densest *allocation* site in the project.

It is **not** the densest CPU cost: 0.6 measures physics, collision, math and
game together at 4.1% of busy CPU, against 8.6% for `hud.ts` alone. Do this phase
for the GC tail (0.6, and finding 10 in the docs), and describe it that way.

### 1.1 `traceInternal` builds a fresh `TraceWork` per trace — `src/collision/trace.ts:608`

    const tw: TraceWork = {
      start: vec3(), end: vec3(), size: [vec3(), vec3()],
      offsets: [vec3() x8], bounds: [vec3(), vec3()], extents: vec3(),
      ...
    };

**15 `Float32Array`s plus 4 array literals plus the object, on every single
trace.** Thousands per second. Move to one module-level `TraceWork` instance.

**`vec3()` returns *zeroed* memory and a pooled object would not**, so every
field needs proving written-before-read on **both** the `positionTest` and the
sweep path, or explicitly zeroing. In practice all of them are written
unconditionally except one:

- `tw.extents` is written **only** when `!tw.isPoint` (`trace.ts:691-693`) and
  read on the axial-plane path at `trace.ts:349` with no guard, so a pooled
  `TraceWork` hands a point trace the previous box trace's extents.
- **Corrected from this plan's first draft: that is benign, not a silent
  correctness bug.** `offset` only widens the span of each child the walk
  descends into, so a stale value is strictly *more* conservative — more leaves
  visited, never fewer — and the leaf test reads `tw.start`/`tw.end`, not the
  walk's midpoints. It costs time, not correctness. This is the same argument
  id's own source makes about the non-axial constant offset ("this is silly ...
  behaviourally identical").
- Zero it anyway: it is free, and the alternative is leaving the next reader to
  re-derive all of the above. But no test will fail if you forget — see 0.5.

**Reentrancy.** A single module-level `TraceWork` is only safe if traces never
nest. `traceWithEntities` (`src/collision/clip.ts:79`) calls `boxTrace` for the
world and then `clipMoveToEntities` calls it again per entity — *sequentially*,
never nested, and it already keeps a module `scratch: TraceResult` on exactly
that reasoning (`clip.ts:66-69`). Confirm the same for the submodel path
(`trace.ts:566`) and for patch tracing before relying on it, and write the
conclusion into the file as a comment — the next person to add a
trace-inside-a-trace needs to be told.

### 1.2 `traceThroughTree` allocates two `vec3`s per node visited — `trace.ts:407,423`

`mid` and `mid2` are allocated inside the recursive descent, so the cost scales
with tree depth times traces. This is the single hottest allocation in the
project.

**Not** a single shared buffer: `mid` is passed *into* the recursive call as
that call's `p2` and stays live across the deeper frames. Use a **depth-indexed
scratch stack** — preallocate an array of `vec3` pairs sized to max tree depth
(or grow on demand once), and index it by recursion depth passed down as a
parameter. Assert/grow rather than overflow.

**No test covers this**, which is the exception in phase 1 rather than the rule.
A shared-buffer version passes all 1151 tests, including a scenario built to be
sensitive to leaf selection, with a byte-identical leaf-visit sequence (0.5,
finding 3). The reasoning above is still right, and a real `.bsp` has a deeper
and less regular tree than `writeBsp` produces — but this change has to be
carried by review, not by a gate. Run the `OA_MAP` suite on it.

### 1.3 Position-test path — `trace.ts:671-676`

`lmins`, `lmaxs`, and `const leafs: number[] = []` per call. Pool all three;
`boxLeafnums` already takes an out-param (`trace.ts:484`), so the array just
needs `.length = 0` instead of a fresh literal.

### 1.4 Function-local vectors in pmove/slidemove

Per tick, from the survey:

- `slidemove.ts:67-72` — `endVelocity`, `clipVelocityTmp`, `endClipVelocity`,
  `dir`, `end`; `slidemove.ts:88` — `planes: Vec3[]` of **five** `vec3()`s;
  `slidemove.ts:255-256` — `up`, `down`.
- `pmove.ts` — `vec` (159), `flatforward`/`spot` (423,426), `wishvel`/`wishdir`
  in all four accelerate paths (484/498, 549/555, 636/643, 790/796), `point`
  (1027, 1077, 1105, 1190).

~20 `Float32Array`s per tick, 125Hz. Move each to module scratch. Same
discipline as 1.1: `vec3()` zeroes, pooled scratch does not — every one of these
must be fully written before read. Most are, since they are built immediately
after declaration, but `wishvel` at 484/549/636/790 is `vec3()` followed by
component-by-component assignment — check that all three components are assigned
on every branch.

`pmove` is not reentrant; the same reentrancy note as 1.1 applies and should be
stated in a comment.

### 1.5 Per-tick frame objects — `simulate.ts:190`, `game.ts:850`, `main.ts:2839`

- `Simulation.snapshot()` builds an object plus three arrays plus `[...events]`.
- `Game.step` allocates `explosions`/`bounces` arrays every tick
  (`game.ts:497-498`) and a `GameFrame` object literal.
- The loop does `prevOrigin = [f.origin[0], ...]` per tick (`main.ts:2839`).

`prevOrigin` is unambiguous — reuse a preallocated triple.

The frame objects need a **named retention audit** before pooling, because a
reused frame that someone stored is a correctness bug, not a perf one. Audit
every consumer of `f`: `pendingResults` (snapshots scalars — check), the
`runSpeedSamples.push(f.speed)` path (a number, fine), `litExplosions.push({
origin: [...e.origin] ... })` (already copies — good), `f.events`, `f.items`,
`f.course`, `f.moverEvents`, and the ghost recorder. If any consumer keeps a
reference past the tick, that type stays unpooled and the reason gets written
down.

`Simulation.run()` and `Game.run()` return `Frame[]` and are used by tests and
tools — those must keep allocating fresh snapshots, so pooling belongs behind a
separate `stepInto(out)` entry point rather than by changing `step()`.

## Phase 2 — the per-frame render block in `main.ts`

### 2.1 `map-lights.ts` `nearest()` — the biggest render-side allocator, `map-lights.ts:394-408`

    const scored = from.map((light) => ({ light, distance: Math.hypot(...) }));
    scored.sort((a, b) => a.distance - b.distance);
    return scored.slice(0, count);

Called **twice per frame** (points and cones) over what its own comment calls
"a few hundred lights", allocating one object per light plus the sorted array
plus the slice — call it ~600 objects and 4 arrays per frame, ~40k objects/sec.

Map lights **never move**. Replace with an O(n·k) insertion scan into
preallocated result slots — `k` is `points.length`, a handful. No array, no
sort, no closures, identical output because the comparison is the same distance.
Verify the tie-break: `Array.prototype.sort` is stable in V8, so the scan must
insert *after* equal distances to reproduce the current order exactly.

Further precompute is available if profiling asks for it — the viewer moves
smoothly, so the top-K set is highly temporally coherent — but do the allocation
fix first and measure before adding a cache with its own invalidation bugs.

### 2.2 `sampleLightGrid` / `applyDynamicLights` — `light-grid.ts:164, 307`

`sampleLightGrid` allocates 6 arrays plus the returned `EntityLight` per call
(`light-grid.ts:168-170, 181-182, 194-198`). `applyDynamicLights` allocates
another (`:317`).

Two changes:

- **Out-param forms.** `sampleLightGridInto(grid, point, out)` and an in-place
  `applyDynamicLights`. Keep the existing allocating wrappers for non-hot
  callers so nothing outside the loop has to change.
- **Precompute for items.** `main.ts:3289-3293` calls `itemScene.relight(...)`,
  which resamples the light grid *per item, per frame*, whenever any dynamic
  light is live. Items **do not move**, so their grid sample is fixed — cache it
  per item at load and per frame apply only the dynamic-light term on top of the
  cached sample. Same math, same inputs, invariant half hoisted. The code
  already knows this: the comment above that block says items' grid light is
  fixed; the caching just was not carried through to the sample itself.

### 2.3 `scene-lights.ts` `set()` — `scene-lights.ts:216-238`

Two `filter`s, a `new Array`, a spread-concat and a `slice`, every frame. Same
result from index loops over preallocated arrays. The partition is stable and
must stay stable — the comment at `:212-217` explains that reordering makes a
light flicker as it changes rank.

**Do not** "optimize" by toggling `light.visible`; `scene-lights.ts:255-262`
documents that visibility is hashed into three's light configuration and
flipping it recompiles every material that sees the light. The parked-caster
handling stays exactly as written.

### 2.4 `updateLights` — `main.ts:2458`

`const live: DynamicLight[] = []` plus one object literal per rocket, plasma,
explosion, muzzle flash and quad glow, every frame. Reuse the array
(`length = 0`) and a small pool of `DynamicLight` records.

**Retention audit first:** `lights.set(live, ...)`, `sceneLights?.set(live)` and
`liveLights = live` (`main.ts:2545-2548`). `dynamic-lights.ts:165` does
`[...lights].sort(...)`, which copies — check the rest of both consumers, and
confirm nothing holds `live` past the frame before pooling it.

### 2.5 `player-anim.ts` — CPU vertex lerp that is sometimes thrown away

`AnimPart.update` (`player-anim.ts:42-83`) runs `lerpSurfaceFrames` over every
vertex of every surface and sets `position.needsUpdate` / `normal.needsUpdate`,
forcing a full buffer re-upload — for the player *and* the ghost, every frame.

Three skips, none of which change what is drawn:

- **Hidden avatars.** `main.ts:3702` applies `hideForFpv` *after* the render, so
  in first person the player avatar is invisible while `animatedPlayer.update`
  (`main.ts:3494`) keeps paying the full lerp and upload every frame. Skip the
  update when the object is not visible. Because the hide is applied after
  render, verify the very first fpv frame still gets one update — do not
  introduce a frame where a newly-shown model has stale vertices.
- **Unchanged frames.** Cache the last `(frameA, frameB, lerp)` per part and
  return early when identical. A held or idle animation re-lerps the same two
  frames to the same weight every frame today.
- **`animationFrame`** (`src/assets/animation.ts`) returns a fresh
  `{ frameA, frameB, lerp }` object per part per frame — give it an out-param.

Check `lerpTag` on the tag chain for the same pattern.

### 2.6 Small, safe, mechanical

- `effects.ts:178` and `explosion-fx.ts:378` — `for (const pool of [this.a, this.b])`
  allocates an array per update call. Hoist to a module constant.
- `main.ts:2911-2913` — `vec3()` for `forward`/`muzzle` on fire; scratch.
- `main.ts:3341, 3452` — the laser's and blob shadow's `vec3(...)` per frame;
  scratch.
- `aim.ts:168` — `options.trace(results, muzzle, vec3(), vec3(), end, ...)`
  allocates two zero vectors per laser trace, per frame. One shared frozen zero

- `hud.ts:593` — `Math.max(cap, ...samples.map((s) => s.speed), 1)` allocates an
  array *and* spreads it into the argument list (which is also a stack risk as

## Phase 2A — three.js per-frame overhead — MATRIX HALF DONE

53% of busy CPU, and the profile names the parts. **The matrix rows below are
done** (see finding 12) and were worth about 3% of busy CPU — a 12-19% reduction
in the scene graph's matrix walk, measured by timing `scene.updateMatrixWorld()`
directly, because `npm run profile` could not resolve a saving that small. The
uniform-node rows are not started and are the larger remaining target.

The correction this phase forced on the plan: three.js is 53%, but **the matrix
family is only 10% of that**, so 2A was never going to be the headline the
ordering table implied.

| ms | % busy | function | what it is |
|---|---|---|---|
| 832 | 3.6% | `updateMatrixWorld` | scene-graph transform walk |
| 826 | 3.5% | `updateByType` | node-material uniform update |
| 729 | 3.1% | `compose` | position/quaternion/scale → matrix |
| 719 | 3.1% | `get value` | uniform node evaluation |
| 464 | 2.0% | `updateNode` | ditto |
| 441 | 1.9% | `_renderObjectDirect` | per-draw submission |
| 439 | 1.9% | `_projectObject` | frustum-cull walk |
| 417 | 1.8% | `multiplyMatrices` | |
| 374 | 1.6% | `updateMatrix` | |

Every one of those scales with **how many objects are in the scene graph** and
**how many of them we touch each frame**, and the same three transformations from
the top of this document apply — none of them changes what is drawn:

- **Skip.** `updateMatrixWorld`/`updateMatrix`/`compose` recompute a transform
  for every object whose `matrixAutoUpdate` is on, every frame, moved or not. The
  world mesh, the map lamps, the item pedestals and the mover groups are static
  between events. Setting `matrixAutoUpdate = false` on them and calling
  `updateMatrix()` only when something actually writes a transform is
  output-identical by construction, and it is most of the 3.6 + 3.1 + 1.8 + 1.6.
  **Audit first**: anything the code moves per frame (missiles, the player, the
  ghost, sky, decals, sprites) must keep auto-update or be updated explicitly.
- **Skip.** `_projectObject` walks the whole graph each frame. It shrinks with
  object count — worth checking how many `Object3D`s the world mesh creates, and
  whether per-surface objects can be merged or parented under fewer groups.
- **Skip.** `updateByType`/`updateNode`/`get value` re-evaluate uniform nodes.
  Uniforms fed from a constant should not be re-read per frame; the shader clock
  and the light arrays legitimately are.

This phase is **not** in the original three-transformation contract's easy half —
it touches the renderer, and a mistake here changes pixels rather than timings. It
therefore needs the screenshot A/B from phase 4 step 5 on every change, not just
at the end. But it is half the frame, and no amount of phase 1 reaches it.

## Phase 3 — the HUD — DONE

Here the dominant cost is **DOM invalidation**, not GC — but both are present.

### 3.0 `debugRow` ran whether or not the panel was visible — DONE

`hud.ts:1197-1216`, and this is the single most expensive function in the project
(1130ms, **4.8% of busy CPU**, more than all of `src/physics/` and
`src/collision/` combined by a factor of three):

```js
elDebug.classList.toggle('hidden', !debugVisible);   // <- a CSS class
elDebugGrid.innerHTML = '';                          // <- NOT gated on it
const debugRow = (label, value, color) => {
  const span = document.createElement('span');
  span.innerHTML = `${label} <b …>${value}</b>`;
  elDebugGrid.appendChild(span);
};
debugRow('pos', …); … six of them, every frame
```

The visibility toggle is a class. The teardown and rebuild under it are **not
gated on `debugVisible`**, which defaults to `true` (`hud.ts:1081`). So the frame
spends ~5% of its CPU building six DOM nodes, six template strings, a closure and
an `innerHTML` parse for a panel that may not be on screen at all.

**Done**, and in both halves, because the gate alone was not enough: `debugVisible`
defaults to `true`, so the common case is the panel being *open* and the rebuild
running legitimately.

1. The block is now gated on `debugVisible`, so a hidden panel costs nothing.
2. The six rows are permanent and each write is dirty-checked, so an open panel
   costs six string compares instead of a teardown, six `createElement`s, six
   `innerHTML` parses and six `appendChild`s.

One detail worth keeping: the value's colour is written with
`setAttribute('style', 'color:#ffd166')`, **not** `.style.color`. The CSSOM
re-serialises the latter as `color: #ffd166;` — same pixels, different markup —
and the DOM gate compares markup. Reproducing the original template exactly cost
two characters and kept the gate meaningful.

`hud.update` writes on the order of 40–60 `textContent` / `style.*` /
`classList` properties every frame (`hud.ts:1147-1290+`), unconditionally.
Assigning `textContent` replaces the text node even when the string is
identical, which dirties style and layout for that subtree; assigning
`style.color` to the same string re-parses it. Most of these values change
rarely — armor, weapon name, ready state, the phase badges — and the speed
readout only changes when the integer changes.

- **Dirty-check every write — DONE.** `setText`, `setHtml`, `setStyle` and
  `setAttr` each remember what they last wrote to an element and skip the
  assignment when nothing changed, backed by one `WeakMap`. Every per-frame
  write in `update()` now goes through them; `setMapName`/`setMode` do not,
  because they are not per-frame and caching a property that something else also
  writes is the one way this can be wrong. That rule is written into the code.
- **The splits table — DONE, and it was a second `debugRow`.** It did
  `innerHTML = ''`, then an `innerHTML` for the header, then three
  `createElement`s per row, every frame a course was loaded — nine elements and
  two subtree reparses per frame for a table that changes when a checkpoint is
  crossed. The rows are now pooled; surplus ones are *detached* rather than
  hidden, because `innerHTML = ''` used to leave exactly `rowCount` rows and the
  markup has to match. `test/render/hud-dom.test.ts` grows the table to seven
  rows and back to five to check that bookkeeping in both directions.
- **NOT throttled to `REFRESH_MS`.** The first draft of this plan suggested
  refreshing the debug readout at `stats.ts`'s 500ms cadence instead of per
  frame. That would change observable output — the numbers would visibly update
  twice a second instead of sixty times — and the brief was explicitly that
  output must not change. Dropped.
- **The `HudData` literal** in `main.ts` is rebuilt every frame with four
  conditional spreads, each of which allocates. Replace with a persistent
  mutated object — **but only after confirming `hud.update` does not store the
  reference.** It appears to read synchronously; verify, including the
  speed-graph sample path, which pushes derived values rather than the object.
  **Still outstanding**; it is on the `main.ts` side of the boundary and is
  allocation rather than DOM work, so it belongs with phase 2.

### 3.2 What phase 3 actually bought

Measured with a 20 000-frame A/B of `hud.update()` under happy-dom, driving a
realistic in-game frame (run clock, splits, strafe gauge):

| | before | after |
|---|---|---|
| debug panel visible | 967.5 µs/frame | **197.9 µs/frame** |
| debug panel hidden | 961.4 µs/frame | **182.7 µs/frame** |

happy-dom is not Chrome, so treat the ratio rather than the absolute numbers as
the result — and note the direction of the error: Chrome's `innerHTML` parse and
style invalidation cost relatively *more* than happy-dom's, so the real saving is
if anything larger. The trace put `hud.ts` at 8.6% of busy CPU
(`debugRow` 4.8% + `update` 3.8%).

Verification that nothing moved:

- `test/render/hud-dom.test.ts`, 13 cases, whole-subtree markup, including
  idempotence, history-independence, hide/show repopulation and a splits table
  that grows and shrinks.
- The live HUD's `outerHTML` pulled out of **real Chrome** and diffed against the
  unmodified build: identical. That is what validates the `setAttribute` choice
  in 3.0, which happy-dom alone could not.

## Ordering and expected payoff

| Phase | Where | % of busy CPU | Notes |
|---|---|---|---|
| **3.0** | `debugRow` unconditional | **4.8%** | one `if`; the best ratio in the document |
| **2A** | three.js scene-graph + uniforms | **53%** (a share of it) | biggest block; touches the renderer |
| **3.1** | the rest of the HUD | **3.8%** | dirty-check ~50 DOM writes |
| 2.1-2.6 | `main.ts` per-frame block | part of `src/render/` 10.2% | `map-lights` is the allocator |
| 1.1-1.5 | physics, collision, math | **4.1% total** | trims the GC tail, not the mean |

Phases 1 and 2 are independent and can land separately. Phase 3 is independent
of both. Each phase should be its own commit with its own gate run, so a
golden-replay diff points at one change rather than twelve.

**The order above is measured, not predicted** (0.6), and it is close to the
reverse of this document's first draft. The frame is CPU-bound (8.3ms against
1.6ms of GPU), so all of it is on the critical path — but the sizes are not what
was assumed.

- **3.0 first.** One `if`, ~4.8% of busy CPU, provably output-identical, no
  physics touched.
- **2A next if the goal is the mean.** It is 53% of the frame and this plan
  originally missed it entirely. It is also the riskiest work here, because a
  mistake changes pixels — screenshot A/B every change.
- **Phase 1 last, and honestly described.** Physics, collision, math and game
  together are 4.1% of busy CPU, and GC — the thing phase 1 exists to reduce — is
  1.2%. It is still worth doing: `vec3` at 1.8% is the largest single function we
  own after the HUD, allocation-driven incremental-marking bursts of 10-22ms do
  land inside individual long frames, and the golden gate makes it safe. But it
  is a **tail** improvement, not a throughput one, and reporting it as the latter
  would be false.

The user's brief was "reduce pressure on the GC etc" and "smooth as butter". The
measurement splits those: GC is ~1% and cannot deliver smoothness on its own,
while the tail it does touch is real. Everything else above is the "etc".

## What this plan deliberately does not do

- No arithmetic rewrites in `src/physics/` or `src/collision/` (see the top).
- No LOD, culling-policy, draw-call batching or shader changes — those alter
  what is drawn, and the brief was explicitly "do not change functional output".
  If 0.4 shows the frame is GPU-bound, that is a *separate* plan with a separate
  conversation about acceptable visual trade-offs.
- No change to the fixed 8ms tick or its decoupling from the render loop
  (CLAUDE.md invariant 4).
- No `light.visible` toggling (2.3), and no `Float32Array` → plain-array swaps
  anywhere in physics (invariant 2).
